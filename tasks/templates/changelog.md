## 1.0.0 — 2026-10-25
- Releases: the board has a release number, MAJOR.MINOR.PATCH (major for significant changes, minor for new features, patch for fixes), and this is 1.0.0. The instructions change only with it. `taskctl new` prints the release a request begins under: when it differs from the release at the top of the SKILL.md you read, re-read SKILL.md. A skill updated within the same release says there is nothing to re-read.
- Restarts and updates: no live stream survives a restart of the board (it keeps requests and tasks). The first command about your request after a restart says so (`taskctl: the board restarted at ...`): open its stream again if it had one. The first one after the board moved to another release while your request ran says that too (`taskctl: the board moved to release ... after request ... began`): re-read SKILL.md, even if another session already updated the skill.
- HTTP API: every response carries `X-Tasks-Release` and `X-Tasks-Boot` (new at every start); /api/health gains `release` and `boot_id`, /api/events `boot_id`, every request `release`; the first live write about a request after a restart gains `restarted`, and after a new release `release_changed` (once per request each; never for a replayed write or one from a page).
- Dashboard: a page reloads itself when the board restarts, so it starts over from the board as it is (an open Settings dialog is waited for).

## v3 — 2026-10-08
- Live stream: `taskctl api POST /api/stream '{"url": "http://camera.lan:8554/"}'` shows a network video or audio stream (http, https, rtsp, rtsps, rtmp, rtmps, srt, udp or tcp) beside the dashboard's request list; a newer url replaces it, `taskctl api DELETE /api/stream` closes it and `taskctl api GET /api/stream` shows it. Do this only when your user asks. The board host needs ffmpeg for it.
- HTTP API: GET, POST and DELETE /api/stream and GET /api/stream/media; /api/events gains `stream`; new errors: 410 for a stream that was replaced or closed, and 503 (+Retry-After) while the stream is not connected yet or has 16 viewers.
- Dashboard: the alert settings dialog is now just "Settings" and has a Live stream section for this device: the stream's sound on or off, and its volume.
- Dashboard: a request's page can list its tasks by number, by progress (running, then queued, then finished) or by the latest update first. The settings gain `"tasks": {"order": "number" | "progress" | "updated"}`, the default for every viewer; each device can pick its own. Nothing changes for agents: the API still lists tasks by number.
- Dashboard: the finished requests come a page at a time (10, 20, 50 or 100, per device); every running request is still listed. GET /api/requests takes `offset` to page the finished ones.
- Request streams: `taskctl stream RID URL` shows a network video or audio stream on your request's page; `taskctl stream RID --close` closes it, `taskctl stream RID` shows it, and `show` has a line for it. Do this only when your user asks. One per request (a newer URL replaces it), only while the request runs, and it ends when the request is completed or deleted. The board's own stream (`/api/stream`) stays as it was.
- HTTP API: PUT, GET and DELETE /api/requests/<rid>/stream; every request gains `stream` (its open stream, or null) and every stream object `request_id` (null for the board's own); /api/events and GET /api/stream gain `streams` (every open stream), and the media route plays any open stream by its id. At most 8 streams are open at once; one more, or one for a closed request, is a 409.
- Dashboard: the request list marks a request that has a stream and has a checkbox on it to pick the stream that plays beside the list (one at a time, per device); a request's page always plays that request's own stream, and none when it has none.
- Reports: a request can have one report, a document shown on its own page of the dashboard (`/r/<rid>/report`). When you publish a report as a Claude artifact for a request, send the same file to it with `taskctl report RID FILE --artifact URL` (HTML or Markdown; `-` for stdin), and again after each update, so the board and the artifact show the same. `taskctl report RID --delete` removes it, and `show` lists it. The board renders an HTML report exactly as claude.ai renders the artifact (its skeleton, sandbox and content policy), so send the file you published, unchanged.
- HTTP API: PUT, GET and DELETE /api/requests/<rid>/report (up to 16 MiB) and GET /api/requests/<rid>/report/page; every request gains `report` (null or the report without its content); new events report_updated and report_deleted. Report pages are served from a report port of the board's own (its port + 1 by default; /api/health has `report_port` and `report_tls_port`), in an origin of their own, as claude.ai serves artifacts.

## v2 — 2026-09-28
- Waiting for the user: `taskctl ask ID 'QUESTION'` flags a request or one task as waiting for input (the board pulses it, shows the question, and can chime or send a notification); `taskctl resume ID` clears it. While a request is open, run ask before you stop to ask the user anything or wait for them, and resume once they answer.
- Offline queue: while the board is unreachable, new, start, progress, ask, resume, done and fail are queued on this machine and replayed in order, with their original times, by the next taskctl command that reaches the board. One taskctl replays at a time and no other waits for it. `new` now prints real ids even offline; `add` still prints `offline`. `taskctl flush` replays the queue now and `taskctl ping` shows its size.
- Self-update: when the board's agent instructions change, taskctl updates the installed skill and CLI by itself and says so on stderr; re-read SKILL.md when it does. Only the board the skill was installed from updates it: a command sent to another board with --url or TASKS_URL never changes the skill or the rule. `taskctl update [--force]` does it by hand (it refuses another board unless --force moves the skill there), and TASKS_NO_UPDATE=1 turns it off.
- New commands: `taskctl usage` prints the full HTTP API reference, `taskctl api METHOD PATH ['JSON']` calls any route, and `taskctl changelog` prints this list.
- HTTP API: POST and DELETE on /api/requests/<rid>/attention and /api/tasks/<tid>/attention; new `attention`, `waiting` and `tasks_waiting` fields and `counts.waiting`; GET /api/events; GET, PUT and DELETE /api/settings; GET /api/changelog; POST /api/requests takes an optional client-made `id`; writes replayed with `X-Tasks-Replay: 1` keep their `at` time; every response carries `X-Tasks-Version` and `X-Tasks-Docs`; /api/health adds `docs_version`, `tls_port` and `config_path`.
- Dashboard: waiting requests pulse, show the question and sort first; each kind of event can highlight, change the tab title, play a sound and send a notification, with board-wide settings saved in a settings file and per-device overrides; an optional HTTPS listener makes notifications work on other devices.
- Permissions: the recommended rules are now one allow rule for `taskctl *` plus ask rules for `taskctl run`, `taskctl update` and `taskctl install-rule`, also behind a global option such as --url (the ask rules win, so those three still ask every time); update and install-rule are not pre-approved by the skill, and both refuse any board but the skill's own unless --force.
